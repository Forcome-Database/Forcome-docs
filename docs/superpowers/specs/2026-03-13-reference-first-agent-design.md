# 参考优先代理设计

**状态：** 经过严格审查后修订

**问题陈述**

当前的 Docmost AI Creator 在用户期望的能力方面失败了：当请求包含外部链接、上传的文档、上传的图像或以其他方式明显依赖于证据时，系统仍然可能在实际阅读源材料之前跳入澄清、建议、大纲或起草。

因此，该产品感觉就像是执行仪式的工作流引擎，而不是首先执行明显工作的代理。

解决办法不是“更好的提示”，也不是“更多的阶段”。修复方法是一小组硬执行不变量：

- 必须在生成之前获取所需的证据
- 所需证据失败必须停止执行
- 澄清必须是后备措施，而不是阶段
- 看得见的进步必须反映真实的行动，而不是仪式

## 目标

- 在起草之前阅读所需的来源。
- 当任务在语义上需要外部证据时，在起草之前进行搜索。
- 当无法检索或解析所需证据时停下来并解释。
- 将上传的文件、上传的图像、外部链接和当前页面上下文视为一个统一的证据系统。
- 仅当证据收集后仍有具体未解决的决定时才提出澄清问题。
- 使产品感觉更接近 Codex 或 Claude Code：
  - 首先做明显的工作
  - 在谈话之前收集证据
  - 受阻时停止
  - 避免面向用户的工作流程剧场

## 非目标

- 一阶段重建整个 AI Creator 图。
- 重新设计完整的 UI 状态模型。
- 在同一个变更中使提案/大纲/审稿人行为变得完美。
- 在证明核心行为之前创建大型多层证据合约。

## 核心设计决策

不要首先将这个问题作为大型舞台重新设计来解决。

将其作为**运行时不变量**来解决：

> 如果所需的证据未成功，系统将无法继续进行任何面向用户的起草或规划输出。

这是主要的行为改变。其他一切都是次要的。

## 统一证据模型

所有类似源的输入都应被视为同一类的证据源：

- `reference_url`
- `uploaded_document`
- `uploaded_image`
- `page_context`
- `web_search`

每个证据源只需要一个最小的共享状态：

```ts
type EvidenceItem = {
  kind: "reference_url" | "uploaded_document" | "uploaded_image" | "page_context" | "web_search";
  source: string;
  required: boolean;
  status: "pending" | "success" | "failed" | "timed_out";
  purpose: string;
  error?: string;
};
```

这应该是运行时所依赖的唯一证据。

## 证据规则

### 1.外部链接

如果用户包含一个或多个外部 URL，并且请求表示或暗示“参考此”、“基于此重写”、“总结此”、“模仿此”或以其他方式将任务锚定到链接，则该 URL 将成为必需的证据。

系统在起草之前必须阅读它。

### 2.上传文件

如果用户上传文档并且任务依赖于该文档，则该文档将成为必需的证据。

示例：
- “根据此 PDF，编写入门指南”
- “将这个Word文档重新整理成教程”

如果上传的文档是主要来源，则文档解析失败必须阻止运行。

### 3.上传图片

如果任务依赖于图像内容，图像就成为必要的证据，必须首先经过视觉理解。

示例：
- “根据此屏幕截图编写步骤”
- “解释一下这个建筑图像”

如果需要图像来安全地完成任务，则图像理解失败必须阻止运行。

### 4.当前页面上下文

如果用户要求在当前页面上继续、转换或构建，当前页面就是证据。

如果无法加载页面上下文并且请求需要该页面上下文，则运行必须停止。

### 5. 搜索

当任务依赖于用户尚未提供或从提供的证据中检索到的外部事实时，需要进行搜索。

示例：
- 对新鲜度敏感的要求
- “与当前最佳实践进行比较”
- “最近发生了什么变化”
- 需要外部事实依据的任务

不应仅仅因为请求广泛而触发搜索。当根据现有证据无法负责任地完成任务时，应该触发它。

## 上传处理

上传的文件和图像不应被视为杂项附件。他们应该输入与 URL 相同的证据优先路径。

### 上传文件处理

1.先解析。
2. 尽可能保留结构。
3. 在提问之前使用解析后的内容作为主要证据。
4. 仅当解析的源代码仍然留下未解决的真正决定时才要求澄清。

### 上传图片处理

1.先运行愿景。
2.提取任务相关内容：
   - 用户界面标签
   - steps
   - 警告
   - 关系
   - 图表结构
3. 在提问或起草之前使用该证据。

### 混合证据输入

如果用户同时提供多个证据源，则它们形成一个证据集。

示例：
- 上传的PDF
- 屏幕截图
- 外部自述文件 URL

系统应该：
1.收集所有必要的证据
2. 处理每个需要的源
3. 如果任何所需的源失败则停止
4. 然后才决定是否需要澄清

## 澄清政策

澄清不是一个阶段。这是一个后备。

系统仅应在以下情况下提出问题：

- 证据收集成功或已用尽可用的明显行动
- 执行因特定的未解决的决定而受阻
- 系统可以准确指出缺少的决策

证据后有效澄清的示例：

- 目标受众未知并且会严重改变输出
- 用户没有指定是保留细节还是积极压缩
- 阅读源代码后仍然存在多个看似合理的转换

无效的说明：

- 在阅读源代码之前询问风格问题
- 询问可以自动提取的信息
- 询问是因为系统跳过了明显的搜索/读取操作

## 运行时硬门

这是最重要的设计规则。

在任何澄清/建议/大纲/写入路径可以发出用户可见的输出之前，运行时必须检查：

- do all required evidence items have `status == success`?

If no:

- 发出阻塞状态
- 解释哪些证据失败以及原因
- 停止执行
- 不允许下游发电

这必须在执行代码中强制执行，而不仅仅是提示，也不仅仅是审阅者逻辑。

## 可见的产品状态

保持可见状态最少且有用：

- `reading sources`
- `searching`
- `need clarification`
- `blocked`
- `writing`

不要暴露更丰富的阶梯，除非用户从中获得了可操作的东西。

## 这个阶段故意不试图完美的事情

这些很重要，但也是次要的：

- 提案抑制逻辑
- 轮廓抑制逻辑
- 审稿人的成熟度
- 广泛的可观察性仪表板
- 跨越各个边界的大型合同

他们可以稍后改进。它们不是核心修复。

## 成功标准

用户体验必须满足以下端到端规则：

1. 如果提示包含所需的 URL，系统会在写入之前读取它。
2. 如果任务明确需要搜索，系统会先搜索再写入。
3. 如果所需的链接/文档/图像/页面/搜索步骤失败，系统将停止并解释失败。
4. 如果存在足够的证据，系统不会提出不必要的问题。
5. 如果证据不足，但缺失的决定是具体的，系统会提出一个有意义的澄清问题。

## 阶段 1 Scope

第一阶段应仅实施：

- 单一权威证据推导
- 对 URL、上传的文档、上传的图像和页面上下文进行统一的证据处理
- 所需证据的硬执行门
- 故障停止行为
- 最小可见状态
- 针对核心不良行为的端到端测试

## 阶段 2 Candidates

只有第一阶段可靠工作后：

- 使提案和大纲真正具有机会主义色彩
- 添加更丰富的证据以输出审阅者检查
- 添加更强的可观察性和推出控制
- 当首次证据不足时，添加恢复循环以进行补充研究

## 预期的产品行为

Given:

`参照这个 README 写一份安装指南 https://...`

系统应该：

1.检测URL作为所需证据
2.先读一下
3.读取失败立即停止
4.如果现在任务明确了就直接写
5. 仅当具体的未解决决定仍然存在时才提出重点问题

Given:

“根据我上传的 PDF 和这张截图，写一份操作手册”

系统应该：

1.解析PDF
2. 理解截图
3. 如果任一所需源失败则阻止
4. 在提出任何问题之前使用收集到的证据
5. 仅询问观众/形式/细节期望是否仍无法推断

这是让产品感觉像是一个证据优先的代理而不是一个分阶段的工作流引擎所需的行为转变。
