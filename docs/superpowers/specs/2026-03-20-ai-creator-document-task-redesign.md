# AI Creator 文档-任务重新设计

> Date: 2026-03-20
> 状态：已起草，待用户审核
> 优先级：文档转换 > 选择重写 > 空白页起草
> 决策：用文档任务优先的架构取代聊天优先的 AI Creator

## 1. 执行摘要

目前的 AI Creator 并没有因为模型太弱而失败。它之所以失败，是因为三项根本不同的工作被强制放入一个共享的聊天/工作台 shell 中：

1.选择重写
2. 文档转换
3. 空白页起草

这种耦合会导致明显的问题：

- 用户界面过载
- 选择重写与之前的对话上下文冲突
- 文档优化表现得像完全重新起草
- 逐节写作产生连贯性漂移
- 重复优化过程中源图像和结构丢失

重新设计不应隐藏聊天。它应该删除聊天作为默认的产品隐喻。

新的默认值应该是：

- 本地选择任务的内联重写
- 右侧文档操作中心，用于文档级任务
- 仅当工作流程自动化不足时才打开的专家协作层

## 2. 批判性判断

### 2.1 当前设计有什么问题

当前的设计并不是该产品主要工作的最佳解决方案。

核心问题是它将文档操作建模为消息历史记录。这是错误的抽象。文档任务应表示为：

- 意图
- 来源范围
- 保存模式
- 结构化摘要
- plan
- 差异集
- 待接受的更改
- 应用和回滚

not as:

- 用户消息
- 助理消息
- 活动日志
- 长期对话上下文

### 2.2 为什么当前的section-writer默认值是错误的

分段写作不应成为文档优化的默认路径。

对于严格保留文档转换，正确的原语不是：

- brief
- 蓝图
- 章节作者
- merge

正确的原语是：

- 解析结构和资产
- 生成块或资产感知更改
- 审查差异
- 安全地应用已接受的更改

章节写作仍然有用，但仅限于：

- 空白页起草
- 多文档合成
- 轻松的大范围重写

### 2.3 为什么上传的文件要使用MinerU-first

对于上传的 PDF 和 DOC 工作流程，MinerU-first 和 Docling 后备是正确的解析策略。

原因：

- 最敏感的故障是图像到文本的对应关系被破坏
- 严格保存需要布局块、图像块、标题结构和局部周围文本
- 纯文本提取是不够的

因此：

- 上传文档优化：MinerU-first，Docling后备
- 当前页面优化：首先编辑区块树和页面结构，而不是MinerU

## 3. 确认的产品要求

### 3.1 优先级和范围

- 所有三种情况仍在范围内
- 优先顺序为：
  1. 文档转换
  2.选择重写
  3.空白页起草

### 3.2 文档转换要求

- 支持两种模式：
  - 严格保存
  - 轻松优化
- 默认模式是严格保存
- 严格保存应尽可能保留结构、图像、表格和代码块
- 宽松的优化可以重新排序结构，但不得破坏含义或图文对应
- 上传源优化和当前页优化共享一个主要产品流程
- 提供文件时，上传的源是默认的主要输入
- 当前页面仅在明确请求时参与上传源优化
- 当前页面优化比上传源优化轻，但仍必须至少保留图像和表格

### 3.3 查看并应用要求

- 默认审核模式是 diff-first
- 审核粒度参差不齐：
  - 默认为块级
  - 文本块内可扩展的细粒度文本差异
- 接受和拒绝操作应该构建一个待定的更改集
- 最终应用应该是明确的
- 最终应用写入实时文档，并且必须自动创建回滚快照

### 3.4 选择重写要求

- 两种交互模式可以共存：
  - 内嵌编辑器-本地预览流程
  - 需要时面板辅助流动
- 默认选择重写保持内联
- 选择重写不得继承原始聊天历史记录
- 选择重写可能为：
  - 选择快照
  - 当地背景
  - 结构化当前文档任务摘要
- 如果文档任务处于活动状态，临时选择重写仍必须作为独立的临时操作运行

### 3.5 协作要求

- 右侧面板应默认仅显示文档级任务
- 面板不是一般的聊天界面
- 面板默认应充当文档操作中心
- 复杂的任务可以自动升级到专家协作层
- 用户必须能够关闭深度协作
- 专家协作层位于右侧面板内，而不是作为单独的页面
- 协作层必须输出结构化决策，而不是自由格式的历史记录

### 3.6 空白页起草要求

- 小型起草任务可直接起草
- 较大的起草任务必须首先确认概要或大纲
- 空白页起草的优先级低于文档转换和选择重写

## 4.产品原理

AI 创作不再以聊天为中心。它以文档任务为中心。

产品原理是：

> 默认为作用于文档的保存优先、可审查、回滚安全的工作流程。仅当工作流程不足时才升级到受控协作。

## 5.信息架构

### 5.1 第 1 层：内联重写

目的：

- 仅限本地选择任务

主要用户体验：

- 更换
- 在下面插入
- retry
- 丢弃

属性：

- 短暂的
- 没有长期的任务历史记录
- 不依赖主面板消息流

### 5.2 第二层：文档操作中心

目的：

- 当前页面优化
- 上传文档优化
- 空白页起草

默认形状：

- 任务标题
- 来源范围
- 保存模式切换
- 结构化任务摘要
- 需要时进行计划预览
- 差异审查
- 待定更改集
- 应用和回滚控制

该层不是聊天 UI。

### 5.3 第三层：专家协作层

目的：

- 澄清复杂的约束
- 确认高影响力计划
- 处理保留降级请求
- 解决多文档冲突
- 支持复杂的合成任务

它应该仅在需要时出现在文档操作中心内部，并且应该在做出决策后折叠回结构化任务状态。

## 6. 状态模型

### 6.1 核心对象：DocumentTask

推荐领域：

- `taskId`
- `taskType`
- `sourceScope`
- `mode`
- `complexity`
- `status`
- `taskSummary`
- `confirmedDecisions`
- `plan`
- `diffSet`
- `pendingChangeSet`
- `snapshot`
- `rollbackRef`
- `riskFlags`

### 6.2 内联重写任务

推荐领域：

- `selectionSnapshot`
- `localContext`
- `taskSummaryRef`
- `candidateResult`
- `actionType`
- `status`

该对象必须独立于 `DocumentTask`。

### 6.3 专家协作状态

推荐领域：

- `reason`
- `question`
- `options`
- `recommendedOption`
- `confirmedDecision`

这是 `DocumentTask` 的子状态，而不是顶级消息流。

## 7. 后端引擎拆分

### 7.1 内联重写引擎

用于：

- 选择重写
- 局部改造
- 快速内联操作

行为：

- 单步工作流程
- 仅本地上下文
- 仅候选人结果

这应该与文档任务引擎分开。

### 7.2 文档任务引擎

这是文档级工作的主要引擎。

它应该在内部支持两种不同的策略。

#### A. 保存补丁流程

用于：

- 严格保存文档优化
- 当前页面优化
- 上传文档优化

行为：

- 解析结构和资产
- 地图块和源资产
- 生成结构化差异
- 允许审查
- 构建待接受的集合
- 应用回滚

此流程必须是文档转换的默认流程。

#### B. 草案和合成流程

用于：

- 空白页起草
- 多文档合成
- 轻松的大范围重写

行为：

- brief
- 概要或计划
- 草稿生成
- 评估器和优化器循环
- 回顾

这就是章节写作可能仍然存在的地方。

### 7.3 专家协作作为子层

协作层不是第三引擎。它是文档任务引擎在以下情况下使用的受控决策阶段：

- 影响力高
- 计划需要确认
- 无法保证保存
- 多个源文件冲突

## 8. 解析策略

### 8.1 上传文件

Use:

- MinerU-first
- 文档后备

解析器必须保留：

- 标题层次结构
- 文本块
- 图像块
- 桌子块
- 可能的话代码或结构化块

### 8.2 当前页面

Use:

- 编辑器块树
- ProseMirror 或 TipTap 结构
- 现有页面资源引用

不要通过 MinerU 路由当前页面优化。

## 9. 默认安全规则

### 9.1 图片

严格保存：

- 如果图像位置不确定，请将原始图像保留在原始位置

轻松优化：

- 更喜欢原来的位置
- 仅当当前安置明显不合适时才建议搬迁

### 9.2 表、代码块、Mermaid

严格保存：

- 如果无法进行安全转换，请保持这些块不变并仅优化周围内容

### 9.3 模式降级

如果不能严格保存：

- 不要默默降级
- 在切换到宽松优化之前请求明确的用户确认

## 10. API 方向

新合同应围绕文档任务和变更集，而不是原始助理消息。

推荐的端点系列：

- `POST /api/ai/inline/rewrite`
- `POST /api/ai/document-tasks`
- `POST /api/ai/document-tasks/:taskId/plan`
- `POST /api/ai/document-tasks/:taskId/diff`
- `POST /api/ai/document-tasks/:taskId/review`
- `POST /api/ai/document-tasks/:taskId/apply`
- `POST /api/ai/document-tasks/:taskId/rollback`
- `POST /api/ai/document-tasks/:taskId/collab`

主要的有效负载应该是：

- `taskSummary`
- `confirmedDecisions`
- `plan`
- `diffSet`
- `pendingChangeSet`
- `assetImpact`
- `riskFlags`
- `rollbackRef`

not:

- 原始消息历史记录
- 合并 markdown 作为唯一的输出

## 11. 保留、重新定位、退休

### 11.1 Keep

- 内嵌人工智能菜单功能
- SSE 和会话基础设施
- MinerU-优先解析方向
- 回滚和冲突恢复概念

### 11.2 重新定位

- brief
- 蓝图
- 回顾
- 评估
- 修复工具

这些应该服务于综合和协作流程，而不是文档优化的默认中心。

### 11.3 作为默认模型退役

- 当前的 AI Creator 工作台 shell
- 文档树加上实时草稿加上活动日志作为主要布局
- 文档优化默认为节编写器和合并
- 聊天记录作为主要任务状态模型

## 12. 迁移顺序

### 阶段 1: front-end cutover

- 替换当前的工作台 UI
- 介绍三层产品模型
- 将选择重写与文档任务状态隔离

### 阶段 2: task-state cutover

- 介绍`DocumentTask`
- 用任务优先状态替换消息优先会话状态

### 阶段 3: API shell cutover

- 添加文档任务端点
- 如果需要，将现有基础设施保留在适配器后面

### 阶段 4: optimization engine cutover

- 使保存补丁流成为文档转换的默认值
- 仅针对综合场景保留基于部分的生成

### 阶段 5: legacy cleanup

- 淘汰旧的 AI Creator 工作台外壳
- 删除旧的创建者条目角色
- 删除不再属于主模型一部分的消息胶水

## 13. 最终建议

推荐的重新设计是：

- 不隐藏聊天
- 不聊天重新换肤
- 不是章节作者优先

It is:

- 本地工作的内联重写
- 文件级工作的文件任务优先运营中心
- 仅当工作流程自动化不足时才控制专家协作

这是产品实际优先级最可靠的路径：

- 保存优先的文档优化，具有可审查、回滚安全的应用程序。
